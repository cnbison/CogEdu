## 1. 总体判断

**架构和认知内核的方向是对的，工程执行质量明显超出多数同类项目；但截至本次复盘，最大的风险不在架构层，而在"内容层"几乎是空的——而这恰恰是产品定位（K12 数理化）的核心。**

原第五部分列出的两个产品级风险（生成延迟、UI 双轨技术债）**已由维护者解决，本文档不再重复展开，后续复盘可视为已结项**。本次修正的核心议题是内容层。

## 2. 分层评估结果

### 2.1 认知内核 —— 扎实，可以放心，暂不需要投入

- `lca/l4_optimization/pomdp_solver.py` 的 `PBVI` 是完整实现（`AlphaVector` / `backup_step` / `reachable_belief_points` / 收敛判断），代码级核查确认非占位。
- 状态变更收敛到 `BeliefUpdator.apply` 单一入口，`InferenceEngine`（纯推断）/`BeliefUpdator`（唯一写点）的读写分离在代码里可验证。
- `dual_agent/` 的抗幻觉设计（`belief_check.py` / `experiment_design.py` / `human_review.py`）是真实校验逻辑，非摆设。
- **结论**：内核算法层面不需要大改，也不建议现在花精力对标 `h2r/pomdp-py` 之类外部实现——PBVI 正确性已有内部收敛测试锁定，边际收益低，不是当前该投入的方向。

### 2.2 命名与实质的落差（需要对外沟通时澄清，非代码问题）

- `motivation/profile.py`（208 行）是 4 维时序（frustration/engagement/confidence/recent_trajectory）的启发式打分，不是完整需求动力学模型。
- `twin/consistency.py`（263 行）是 5 条规则的**一致性校验器**，不是仿真意义上的数字孪生。
- POMDP 的 4 个状态（Engaged/Frustrated/Bored/Confused）建模的是**情感/动机状态**，不是知识掌握状态——知识掌握由另一套 5D MIRT + Bloom + Q 矩阵负责。
- **结论**：分工本身合理，但"认知操作系统""数字孪生"等命名容易让人（包括未来合作方）对系统能力产生超出实际的预期。**建议对外沟通时明确区分"POMDP 策略"与"知识诊断"两套系统的边界。**

### 2.3 内容层 —— 当前最大的方向性风险（本次复盘核心结论）

- `cogedu/goal/registry.py` 的 `DEFAULT_CAPABILITIES_LIST` 目前仍是 5 条 **Python 编程**能力（变量/循环/函数/条件/字符串），非数学/物理/化学。
- `data/q_matrix.json`（数学学科）实际内容**全部是占位符**（`problem_text: "【待教师填写】"`），32 道题一道真题都没有。
- Bloom Goal Library、干预类型、误概念库目前全部建立在这个空的 Q 矩阵之上。
- **结论**：整个系统（内核 + 呈现引擎 + 白板语音 + 家长报告）**从未用一份真实数理化内容完整跑过一次端到端**。1964 个测试用例、灰度脚本验证的是"管道通不通"，不是"给一个真实学生讲一次真实知识点，效果好不好"。继续向 Phase 4/5/6 堆工程能力，等于在一个未被真实内容验证过的地基上继续加高——如果真实内容跑起来后发现 Bloom 分层/误概念库/干预类型设计与实际教学场景对不上，上层的可视化和扩展工作可能要返工。

### 2.4 呈现引擎缺一个安全闸（待补齐）

- `dual_agent` 的抗幻觉机制（信念分布合法性检查、实验设计校验、人工复核触发）**未被 `cogedu/presentation/` 引用**。
- 呈现引擎生成的讲解内容（LaTeX 公式、白板动作、语音讲解词）直接由 LLM 产出后展示给学生，没有经过任何自动或人工正确性校验。
- **结论**：这是直接面向 K12 学生的数理化讲解内容，风险量级高于"教师端看到一个错误诊断标签"。与内核那套抗幻觉设计的谨慎程度不成比例，建议尽快补齐（哪怕先做成"低置信度内容标记待复核"的轻量版本，而非全量人工审核）。

### 2.5 已解决风险（确认结项）

- ~~生成延迟（10~25 分钟黑盒等待）~~ —— 已解决。
- ~~UI 双轨技术债（legacy 静态页 + React 并存）~~ —— 已解决。

### 2.6 扩展性 —— 设计良好，基础可用

- `cogedu/domain/` 已有 `EducationDomain` / `ScienceDomain` / `CareerDomain` 的抽象层，Plugin SDK 的零 mutation 原则执行到位，这是面向未来多学科/多场景扩展的良好基础，不需要现在调整。
- 唯一的耦合风险：呈现引擎与 TTS 强绑定 MiniMax（+ Moonshot 备份），供应商集中度较高。现阶段不紧迫，产品化到一定量级后需评估多供应商容灾。

## 3. 核心决策：内容层学科范围明确

**经维护者确认，内容层不再是待定的"先做 Python 占位、以后再扩展"，而是直接按可扩展的多学科内容架构，明确先做三门课程：**

- **初一数学**
- **初一物理**
- **初一化学**

这三门课程作为"可扩展内容科目"架构的第一批落地对象，Python 编程能力（`DEFAULT_CAPABILITIES_LIST` 现状）降级为内部测试用的占位数据，不再代表产品实际学科范围。

### 3.1 对 Goal Ontology / Capability 体系的影响

- `cogedu/goal/registry.py` 的 `DEFAULT_CAPABILITIES_LIST` 需要新增初一数学/物理/化学的 Capability 定义（当前 Python 5 条可保留作为内部测试 fixture，不与生产 Capability 混用，或明确标记为 `domain="internal_test"`）。
- Bloom Goal Library、误概念库需要按三门学科分别建立，不能沿用单一学科的隐含假设去套三门课（数学/物理/化学的误概念模式、Bloom 层级表现形式本身就有差异，需要分别设计，不要"复制数学的模板改改字段"了事）。

### 3.2 对 Q 矩阵内容工程的影响

- 现有 `data/q_matrix.json` 的占位符结构（metadata / problems / instructions_for_teachers）可以保留作为教师协作填写的模板骨架，但需要**尽快组织真实的初一数学/物理/化学教师，填入真题**，而不是继续以空模板存在。
- 建议每门学科先聚焦 1-2 个具体知识点（例如数学"一元一次方程"、物理"密度"、化学"物质的变化与性质"），每个知识点 15-25 道真题，作为"最小真实闭环"验证素材（见第 4 章）。

## 4. 建议行动项（按优先级）

### P0（在继续 Phase 4/5/6 工程投入之前，建议先做）

1. **三门学科最小真实闭环验证**：数学/物理/化学各选 1 个具体知识点，找对应学科老师标注真实 Q 矩阵（15-25 题/知识点），跑通一个真实学生从答题 → 认知状态更新 → 讲解场景生成的完整流程，人工评估生成内容的教学质量（正确性、讲解逻辑、是否符合初一学生认知水平）。
   - 这一步的价值判断：能验证 Bloom 分层/误概念库/干预类型设计是否真的适配三门学科的实际教学场景，成本远低于继续堆工程能力，但决定后续排期是否需要调整。
2. **补齐呈现引擎的抗幻觉闸门**：将 `dual_agent` 现有的抗幻觉机制（或至少一个轻量版本）接入 `cogedu/presentation/` 的生成出口，优先覆盖数学公式推导、物理/化学概念表述这类高风险内容类型。

### P1（三门学科闭环跑通后推进）

3. **Goal Ontology 三学科扩展**：按 3.1 节，正式为初一数学/物理/化学分别建立 Capability、Bloom Goal、误概念库，不复用单一学科模板。
4. **教师协作填题工作流**：把"教师填 Q 矩阵"从一次性任务变成可持续流程（哪怕先是最简单的表格协作 + 人工审核入库），因为三门学科的内容需求量级会持续增长，不是一次性填完的任务。

### P2（不紧迫，可延后）

5. **内核算法外部对标**：内核质量已确认扎实，暂不需要投入对标外部实现（如 `pomdp-py`）的精力。
6. **LLM 供应商容灾**：现阶段 MiniMax 为主/Moonshot 备的方案可用，产品化到一定用户量级后再评估多供应商降级方案。

## 5. 对现有 Phase 路线图的建议调整

`docs/cogedu-整合技术方案.md` 目前的 Phase 4（证据链可视化增强）/ Phase 5（教学素材接入）/ Phase 6（GeoGebra + 区块化内容扩展）路线图，建议在启动前先完成第 4 章的 P0 行动项。理由：

- Phase 4 的可视化对象（证据链、误概念专项视图）目前建立在空的 Q 矩阵之上，可视化"空内容"没有验证价值。
- Phase 5（教学素材接入）与本文档第 3、4 章要解决的问题高度重叠，建议**合并推进**而不是分开排期——教学素材接入本质就是"把三门学科的真实内容接进来"，这正是当前最紧迫的事，不需要等 Phase 4 走完再启动。
- 建议的顺序调整：**P0 最小真实闭环验证 → 呈现引擎抗幻觉闸门 → 三学科 Goal Ontology 正式扩展（原 Phase 5 提前） → Phase 4 证据链可视化（在有真实内容后再做，可视化才有意义） → Phase 6**。

具体的任务拆分、工作量估算建议按项目既有习惯，在 `cogedu-整合技术方案.md` 中新增章节细化，并遵循"每完成一项任务同步方案文档 + CLAUDE.md + CHANGELOG + README"的既有协作规范。

## 7. 深度复盘补充与拍板结论（2026-09-16，与维护者确认）

本节是在本文档基础上的深度复核与决策记录，全部论断经代码级核查；与第 3-5 章冲突之处**以本节为准**。

### 7.1 四项拍板（2026-09-16）

1. **学科口径修正（覆盖第 3 章表述）**：标准课标下初一没有独立的物理/化学课（物理初二、化学初三开课；浙江《科学》综合课例外），"初一数学/初一物理/初一化学"改为**按学科起始年级**。试点知识点：数学「一元一次方程」（七年级）、物理「密度」（八年级）、化学「物质的变化与性质」（九年级）。
2. **学生端设备口径**：以**横屏平板/电脑为主**（课堂/书房场景），手机为次要场景。
3. **UI 路线：桌面优先重设计**（DeepTutor 式工作台形态，独立立项 UI-R），不采用渐进响应式改造。依据：设备口径已确认横屏为主 + 底栏 5 Tab 已到人机工学上限（Scene/Report/GuardianLinks 三路由已在栏外）+ 白板虚拟画布是 16:9 横屏设计却被压在 720px 竖排版心 + Phase 4-6 新功能（误概念视图/素材库/GeoGebra 探索/概念图）无处安放。
4. **P0 排期：P0-1 先行、P0-2 紧随**——没有真实内容无法校准内容校验器，P0-1 人工评估发现的错误类型正是闸门规则的第一手输入；闭环期间人工评估充当临时闸门。

### 7.2 对本文档的三处修正/补充（代码级核查）

1. **P0-2 接法修正（第 4 章 P0-2 表述据此修正）**：`dual_agent/anti_hallucination/belief_check.py` 检查的是 **BeliefState 分布健康度**（K/P/S/C/X 五维 confidence 合规、低置信 evidence 支撑数、过度自信检测），校验对象是认知状态而非生成内容，**不能直接接入 presentation 出口**。正确做法：借 `anti_hallucination/human_review.py` 的 HumanReviewTrigger 模式（低置信 → 标记 → 复核队列），**新建内容级校验器**挂 `presentation_service` 落库出口前——L1 程序化校验（LaTeX 语法/数值重算一致性/单位量纲）→ L2 LLM 交叉校验（第二模型查公式推导与概念表述）→ L3 低置信 `needs_review` + 教师复核队列。
2. **内容工程量补充（第 3.2 节据此加码）**：除"填 Q 矩阵"外，`web/api/routers/student.py` 的 LLM judge 4 档 partial credit **依赖 Q 矩阵逐题 `partial_credit_rubric` 字段**（现为空）。试点内容三件套 = 真题 + 逐题 rubric + 误概念标注，教师工时按三件套估算。
3. **judge 判分列为同级评估对象（第 4 章 P0-1 评估范围扩充）**：ECOS 时代 judge 判 Python 编程题，数学过程/物理计算的 partial credit 判定难度更高，而 belief 更新全部建立在 judge 输出之上（垃圾进垃圾出）。P0-1 人工评估三个同级对象：讲解内容教学质量、LLM judge 判分质量、Bloom 分层/误概念库/干预类型对三学科实际教学场景的适配度。
